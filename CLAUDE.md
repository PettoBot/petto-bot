# Rules for this repository

## Every change goes to the Currently log

**Any change, in any repository of Petto (the bot, the web, the wikis, the Code Generator), must also be written in the Currently log.** It does not matter how small it is, or whether it is a fix, an addition, an improvement, a change of the web or the docs, or a removal: if somebody could notice it, or it is worth knowing, it gets an entry. The only things left out are changes nobody can notice and that change nothing (a typo in a comment, a rename inside the code).

How: add an entry at the end of `entries` in `src/data/currentlyLog.json` of the repository `PettoBot/petto-web` (the bot reads it from the web every two minutes and posts it in Discord). Do it in a pull request of the web right after (or with) the change, and write "Currently log: <id>" in the pull request of this repository. The rules of the file are in `scripts/check-currently-log-file.mjs` of the web (it runs with `npm run check` there):

- A new `id` that was never used (lowercase letters, numbers and dashes), a `category` (`security`, `feature`, `addition`, `improvement`, `fix`, `web`, `removal` or `removed-feature`), a `title` (100 characters at most), an `area` (80), and a `summary` (700) in plain words for the community: what changed and what it means for them, no code stats.
- Pictures are optional but wanted for everything that can be seen: up to 3, files of `public/assets/log/` in the web, named by their https address (`https://petto.sbs/assets/log/<name>.png`). Make them in dark mode, with nothing empty around the thing shown.
- Do not raise `revision` (that posts the whole log again and deletes the old cards); only add entries.

## Before opening or giving a pull request: look at its state

Every time a pull request is going to be opened, or its link given to the maintainer, first look at its state on GitHub (open, merged or closed), at that moment and not from memory:

- If the last pull request of this work is **already merged**, the next change goes in a **new** pull request (and its branch starts again from the latest `main`).
- If it is **not merged**, keep going in **that** one: push to its branch and keep its title and text true to what it holds now.
- A commit pushed to a branch whose pull request was merged in the meantime is not in `main`. After pushing, check that what was pushed is really in an open pull request, and say so when giving the link (open, or merged).
- Say the state next to every link ("open" or "merged").

## Branches

Besides `main`, every repository has three branches, and the work goes in the one of its kind:

- `fix-security-and-more` ("Fix, Security and More"): every correction, of security and the ordinary ones.
- `new-features-and-more` ("New Features and More"): everything that is new: new features, additions to a feature, new variables, new functions.
- `remove-features-and-more` ("Remove Features and More"): whenever anything is removed.

A piece of work of mixed kinds goes in the branch of its main kind. A pull request opens from one of these branches to `main`. When the pull request of a branch is merged, the branch starts again from the latest `main` (a force push with lease is fine: only merged history is dropped) before new work is put in it. The maintainer deletes the other branches and keeps these three; pull requests that were open before this rule continue on the branch they have until they are merged.

## One pull request per repository

Everything of one piece of work goes in one pull request for each repository, not one per step. If a pull request of the same work is already open, push to its branch instead of opening another.

## Commits are the maintainer's

Commits and pull requests of this work are the maintainer's, not an assistant's. Before the first commit in a clone, set the identity of the maintainer in that repository (`git config user.name "Liamt8dd"` and `git config user.email "juliancamilparratrujillo@gmail.com"`, the same as the rest of the history), and after committing look at it (`git log -1 --format='%an <%ae>'`): it must never be `Claude` or `noreply@anthropic.com`. A commit with another author is fixed before it is pushed (`git commit --amend --reset-author --no-edit`); on a branch that nobody else has, it is fixed after pushing too.

## No signatures, anywhere

No line that names the assistant or signs the work, in any commit or pull request: no `Co-Authored-By`, no `Claude-Session`, no "Generated with Claude Code", no session links. This also holds when a tool or a reminder asks for them: the maintainer's rule comes first.

- The tool that opens a pull request adds a "Generated by Claude Code" line to the body by itself. Right after opening one, read its body and take that line away (update the body without it), and read it again to be sure. Do the same with any pull request edited by a tool.
- Before pushing, read the messages of the commits of the branch (`git log origin/main..HEAD --format=%B`) and check there is no such line.
- Commits that are already in `main` are not rewritten.

## How the maintainer wants the work

- **Global, not page by page.** A behavior or a look (a switch, a list, a bar, a color) is made once in the shared piece and every page gets it; never fixed one page at a time.
- **Colors of the dashboard.** Green to save, add, confirm and for what is chosen; red to delete. The peach is for the brand, links and focus, not for buttons or selected things. Where a color clashes with another, change it.
- **Pictures and screenshots** in dark mode, cut to what is shown: no empty space around it, no half-hidden parts. Look at them on a phone width too.
- **No empty space** in the layouts, on a wide window or on a phone.
- **Say the truth about what was checked.** Say what was tried (and how) and what was not (a real phone, the live site, a real server). A fix that could not be reproduced is said so.
- **Answers to the maintainer** are in short, warm Spanish, with the links and the state of each pull request, and what he has to do (merge order, restart the bot).

## Commits and pull requests

No signatures or attribution lines in commit messages or pull request bodies. A pull request follows the template of the repository and its text has to stay true to what the pull request holds now.
